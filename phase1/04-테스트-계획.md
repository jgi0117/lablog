# 테스트 계획 초안

최종 테스트는 Phase 6에서 하지만, 설계 단계에서 무엇을 어떻게 확인할지 정해 두어야 기능마다 테스트를 같이 쓸 수 있다.

## 테스트 층

- **단위**: 도메인 규칙(`rules.ts`, `progress.ts`), 검색 점수·하이라이트, 값 검증 — Vitest
- **계약**: 저장소 구현이 `backend.contract.ts`를 모두 통과 — Phase 2에 LocalRepository, Phase 9에 Supabase
- **컴포넌트·통합**: 화면 동작(체크, 입력, 필터) — Testing Library + fake-indexeddb
- **E2E**: Journey 1·2·3 — Playwright (Phase 3에서 도입)
- **사용성**: 연구원 과제 기반 관찰 — Phase 6

## 오류 시나리오 → 테스트 케이스

uj.md의 오류와 연결한다. "계약"은 이미 작성한 계약 테스트, "예정"은 해당 Phase에서 작성한다.

- **E1 저장 실패·끊김**: 저장 실패 시 StorageError와 안내 표시, 다시 시도 (통합, Phase 5). 로컬 전용이라 연결 끊김은 영향 없음을 E2E로 확인.
- **E2 실수로 체크**: setDone 해제와 doneAt 비움(계약, 작성됨), 되돌리기 토스트 5초(통합, Phase 3)
- **E3 단계 건너뜀**: completionWarnings(단위, 작성됨), 완료 전 확인창(통합, Phase 3)
- **E4 검색 결과 없음**: 빈 배열(계약, 작성됨), 철자 제안·필터 해제 UI(통합, Phase 4)
- **E5 실수로 삭제**: 소프트 삭제·복원·검색 제외·30일 영구 삭제(계약, 작성됨)
- **E6/E9 동시 수정**: expectedVersion 충돌(계약, 작성됨), 다중 탭 변경 감지(통합, Phase 5)
- **E7 단위·수치 오입력**: 숫자 형식·범위 경고는 막지 않음(단위, Phase 3)
- **E8 복제 후 결과 남음**: 복제 시 체크·메모·결과 비움(계약, 작성됨)

## 테스트 데이터 세트

코드로 생성하는 시드 함수를 `app/src/tests/fixtures/`에 만든다(Phase 2).

- **S**: 실험 5건 (기본 흐름, 상태 3종 모두 포함)
- **M**: 실험 50건, 단계 평균 8개 (일상 사용)
- **L**: 실험 500건, 단계 10,000개 (성능: 검색 2초, 목록 렌더)
- **특수**: 매우 긴 제목(200자), 이모지, 한글 자모 조합, 특수문자, 빈 값, 태그 30개, 단계 100개
- **현실**: Phase 0에서 모은 샘플 기록을 입력한 1세트 (인터뷰 후)

## 성능 기준

- 첫 화면 2초 이내, 체크 반응 체감 즉시(100ms 이내), 검색 입력 후 2초 이내 표시
- 측정: L 세트에서 목록 열기, 검색, 체크 반응 시간을 스크립트로 기록

## E2E 시나리오 목록 (Phase 3·4 작성)

- **J1**: 새 실험 → 단계 3개 입력 → 수행 모드 → 체크·메모 → 결과 입력 → 완료 → 홈에 반영 (+ E2, E3 경로)
- **J2**: 실험 20건 시드 → 검색 → 필터 → 열기까지 10초 이내(타이머 단언) (+ 결과 없음, 삭제 후 복원)
- **J3**: 복제 → 결과 비어 있음 → 수행 (s3 구현 후)
- **데이터 보호**: 내보내기 → 초기화 → 가져오기 후 동일
- **지속성**: 새로고침·탭 닫고 다시 열기 후 데이터 유지
