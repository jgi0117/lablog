# lablog

**라이브 데모**: https://lablog-kgt8.vercel.app/ (브라우저에서 바로 열립니다. 데이터는 그 브라우저에만 저장)

**앱이 실험 순서를 정하고, 사람은 결과 숫자만 넣는** 제품개발 실험 관리 도구. 모인 데이터로 조건 → 결과를 예측하고, 고객 목표를 만족할 조건을 제안한다.

**풀려는 문제(이상 vs 현재)**: 이상은 모든 실험이 같은 틀의 한 표에 있고 그 표가 다음 조건을 계산하는 것. 현재는 기록이 흩어져 있고 입력이 귀찮아 쌓이지 않으며 다음 조건은 짐작이다. 그래서 기능은 둘 — **① 한 곳에 모으기, ② 시뮬레이션(예측·제안)**.

**해결**: 프로젝트에 "무엇을 바꾸고(입력), 무엇을 재고(출력), 어디까지 가야 하는지(목표)"만 적는다. 목표는 보통 **목표값 ± 허용**이다(강도 35 ± 3처럼, 가까울수록 좋고 허용 안이면 만족). 그러면
1. 앱이 입력 범위를 고르게 덮는 첫 실험 조건들을 짜 준다(라틴 하이퍼큐브).
2. 실험 카드에 조건이 적혀 있다. 당신은 결과 숫자만 넣고 "저장하고 다음 →"를 누른다.
3. 완료 실험이 8건을 넘으면 모델이 만들어지고, 목표를 만족할 가능성이 큰 조건을 다음 실험으로 자동으로 이어 붙인다. 기본은 자동(랜덤 포레스트 vs 선형 회귀, 교차검증으로 선택)이고, 모델 탭에서 알고리즘·파라미터·조건을 골라 **직접 학습해 버전으로 저장·적용**할 수 있다. 모델은 **같은 변수를 가진 모든 프로젝트의 실험을 모아** 학습한다(프로젝트 차이는 표시 변수로 배운다).
4. 필수 목표를 모두 만족한 조건이 나오면 "목표 달성"으로 실험이 끝난다(원하면 더 할 수 있다).

모든 데이터는 이 브라우저(localStorage)에만 있다. CSV·JSON으로 내보내고 가져온다. 서버 없음.

## 화면: 상단 탭 셋 — 프로젝트 · 데이터 · 모델

데이터와 모델은 프로젝트를 넘나들기 때문에(같은 변수를 가진 프로젝트를 모아 학습) 프로젝트 안이 아니라 옆에 둔다.

| 탭 | 주소 | 하는 일 |
|---|---|---|
| 프로젝트 | `/` | 카드마다 목표 상태(달성·종료 / 진행 중), 완료·계획 수, "다음 실험 결과 넣기" |
| ↳ 실험 화면 | `/p/:id` | **다음 실험 카드**(조건 표시 + 결과 입력), 목표 현황과 가장 가까운 조건, 목표 추적 차트, 최근 결과, 모델 요약. 설정(`/p/:id/setup`)은 변수·목표·탐색 수·계획 다시 짜기·삭제 |
| ↳ 새 프로젝트 | `/new` | 변수(입력 범위·측정 시점·출력)와 탐색 조건 수 → 첫 계획 자동 생성. CSV로 바로 만들기 |
| 데이터 | `/data?p=` | 고른 프로젝트 + 같은 변수를 가진 프로젝트의 모든 실험을 한 표로(모델이 학습하는 표), 또는 **전체 프로젝트**(변수 이름이 같으면 한 열, 읽기만). 한 쪽에 10건. 칸 바로 수정, CSV 더하기·내려받기, 직접 추가. **입력 점검**: 변수별 박스플롯(기본은 중앙값·IQR로 표준화해 한 축에, 원래 값으로 전환 가능)과 이상치 후보(소수점 실수 ×10·×0.1 표시, 누르면 표에서 찾기). 조건–결과 산점도와 조건별 상관. 전체 백업·가져오기 |
| 모델 | `/model?p=` | 적용 중인 모델의 R²·MAE·RMSE·MSE(모두 교차검증). **직접 학습**: 결과(label)·조건(feature)·알고리즘(랜덤 포레스트, 선형 회귀, k-최근접, 부스팅)·파라미터·교차검증 겹 선택 → 학습 → R²·오차·예측 vs 실제·중요도 확인 → **버전 저장·적용**. 적용한 모델이 제안·예측·다음 실험에 쓰임. 버전 표(파라미터, 조건 수, R², 학습일). 자동 모델은 버전이 없을 때의 기본 |

## 실행

Node.js 24. `app/`에서:

```bash
npm install
npm run dev        # http://localhost:5173
npm run check      # 린트 + 타입 검사 + 테스트
npm run build      # 배포용 빌드 (dist/)
```

main에 올리면 GitHub Pages에 자동 배포된다(`.github/workflows/deploy.yml`). Vercel도 `app/vercel.json`으로 그대로 된다.

## 구조

```
app/src/
├─ domain/types.ts      프로젝트·변수·실험 모델, 목표 판정
├─ services/store.ts    localStorage 저장소(useDb 훅)
├─ services/plan.ts     실험 계획(라틴 하이퍼큐브, 측정 시점 펼치기, 모델 계획), 현황 계산
├─ services/model.ts    알고리즘 4종(RF·능형·kNN·GBM), 교차검증, 버전 직렬화, 예측 구간, 목표 만족 확률, 조건 제안
├─ services/pool.ts     같은 변수를 가진 프로젝트의 실험을 모아 학습(프로젝트 표시 변수)
├─ services/csv.ts      CSV 읽기·쓰기, 백업 JSON, 예전 lablog(실험 노트) 백업 변환
├─ data/demo.ts         예시 데이터(UCI 콘크리트에서 고른 프로젝트 12개, 실험 약 200건)
├─ pages/               HomePage, NewProjectPage, ProjectPage, DataPage, SetupPage
└─ *.test.ts(x)         서비스 14개 + 화면 흐름 4개 테스트
docs/                   문제 정의·설계, 발표자료
```

자세한 설계와 "어디까지 믿어도 되는가"는 [docs/01_문제정의와_설계.md](docs/01_문제정의와_설계.md), 발표자료는 [docs/발표자료.html](docs/발표자료.html).

## 데이터

- 처음 여는 브라우저에는 예시 프로젝트 12개(결합재 4종 × 목표 강도)와 참고 프로젝트 4개(프로젝트에 쓰지 않은 나머지 배합, 학습에만 사용)가 자동으로 들어간다. 공개 데이터 1,030행 가운데 중복 38행을 뺀 992행을 모두 쓴다. UCI *Concrete Compressive Strength*(Yeh 1998, CC BY 4.0)에서 배합을 골라 "목표에서 먼 배합부터 점점 가까워지다 목표 ±허용 안에 들어오면 끝"이라는 실제 프로젝트 모양으로 엮었다(아홉은 끝났고 SM-55·ES-60·HB-70은 진행 중). 같은 변수를 쓰므로 모델은 16개를 모아 992건으로 학습한다. 값은 바꾸지 않았고 프로젝트 이름·고객·목표는 지어낸 것이다. 필요 없으면 각 프로젝트의 설정에서 지운다(다시 넣지 않는다). `app/src/data/concrete/README.md`.
- 예전 lablog(실험 노트) 백업 JSON을 "백업 가져오기"로 넣으면 조건·결과·고객 요구만 옮겨 온다. 절차·메모는 옮기지 않는다.
