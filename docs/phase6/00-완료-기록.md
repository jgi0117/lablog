## 한 일

**실제 브라우저 E2E** (Playwright, `app/e2e/`, `npm run e2e`)
- Chromium(노트북 1440×900), Firefox(노트북), WebKit(iPad Pro 11 가로 1194×834, 터치) 세 곳에서 돈다. 개발 서버를 띄워서 쓰고, 테스트마다 새 브라우저(빈 IndexedDB)로 시작한다.
- 흐름: J1 새 실험 수행, J2 찾기, J3 이어받기, J4 빠진 것 채우기, 백업→삭제→가져오기(다른 브라우저 컨텍스트로 복원), 새로고침·탭 다시 열기 후 유지, 두 탭 충돌, CSV 내보내기, 분석 차트 이상치 점 열기.
- 키보드만으로 새 실험→절차→수행→완료, 검색, 수행 모드 방향키·Space, 차트 점 열기.
- 태블릿 가로·세로·좁은 화면(390): 모든 화면이 가로로 넘치지 않고, 수행 모드의 눌러야 하는 요소가 모두 44px 이상(장갑 기준), 배치가 바뀐다.
- 접근성: axe(WCAG A/AA)로 15개 화면과 대화상자를 검사, 위반 0.
- 성능: 실험 500건·단계 4,000개, 단계 체크 반응.

**E2E가 찾아낸 실제 결함 (모두 고침)**
1. 단계를 Enter로 빠르게 이어서 넣으면 단계가 합쳐지거나 빠졌다 → 입력을 차례대로 처리. 회귀 단위 테스트 추가(`journey1.test.tsx`).
2. 제목 장식 `❦`을 스크린 리더가 읽었다 → 장식은 읽지 않게.
3. 데이터 표에서 숨긴 글자가 표 밖으로 새어 페이지가 가로로 넓어졌다 → 표 영역에 가둠.
4. 차트 점을 눌러 열 수 있는데 `role="img"` 안에 조작 요소가 들어 있었다 → `role="group"`.
5. 표 머리글 단위 글자 대비 부족 → 색 조정, 대비 테스트에 조합 추가.
6. 시험 데이터가 시간대·시각에 따라 "10일/9일"로 달라져 CI(UTC)에서 실패 → 정확히 n일 전으로 고정.

**CI** (`.github/workflows/ci.yml`)
- 린트·타입·단위 테스트·빌드를 시간대 UTC, Asia/Seoul, America/Los_Angeles에서 각각 돈다(시간 의존 결함 방지).
- E2E 작업을 따로 둠(Linux, 세 브라우저). 실패하면 보고서를 올린다.

## 알려진 이슈와 우회

- **WebKit 대량 가져오기 측정 생략**: Playwright의 Windows용 WebKit은 IndexedDB 쓰기가 매우 느리다(훅 없는 `bulkPut`도 실험 100건·단계 800개에 약 14초, 500건은 끝나지 않음). 앱 결함이 아니라 시험 환경 한계라서 이 한 건만 Windows+WebKit에서 건너뛴다. CI(Linux)에서는 돈다. **실제 iPad Safari에서 큰 백업을 가져와 보는 것은 실기기 확인 목록에 넣는다.**
- WebKit에서 키보드 Tab 이동 테스트 4건과 axe 2건은 건너뛴다(Safari는 기본 설정에서 Tab이 링크·버튼에 가지 않고, axe는 엔진과 무관해 Chromium 한 곳에서 본다). 키보드 확인은 사람이 실기기에서 한다.
- 단계 입력의 Enter 연타가 느린 기기에서 입력칸이 잠시 비어 보일 수 있다(저장은 차례대로 된다).

**사용성 테스트** (연구원 3~5명): 과제는 `docs/phase1/02-수행모드-사전검증.md`의 대본을 그대로 쓴다.
1. 샘플 절차로 새 실험을 만들고 수행 모드에서 3단계 체크·메모
2. 지난 실험 3건 검색해 열기(시간 측정, KR1)
3. 결과 기록하고 완료
관찰: 막힌 지점, 오류, 용어. 종료 질문: "지금 쓰는 방식보다 나은가? 어디가 불편한가?"

**KR 평가 준비**: 설정 화면의 사용 기록에서 KR1(검색 후 열기 중앙값·10초 안 비율)과 KR3(완료할 때 빠진 것 비율, 주별 빠진 것)을 내보낸다. KR2(재실험 건수)와 사용률은 파일럿 뒤에 본다. 가드레일(기록 입력 시간)은 사용성 테스트에서 기존 방식과 비교해 잰다.
