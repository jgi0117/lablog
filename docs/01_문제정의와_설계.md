# lablog v3 — 문제 정의와 설계

## 1. 문제

제품개발팀의 실험 관리에서 확인한 불편.

| # | 문제 | 지금까지 |
|---|---|---|
| P1 | **입력이 귀찮다.** 실험마다 절차를 쓰고, 단계를 체크하고, 조건·결과를 이름-값-단위로 적어야 했다 | 실험 노트형 앱(v2)은 기록을 모으는 데는 좋았지만 한 실험을 등록하는 데 클릭이 많았다 |
| P2 | **다음 실험 조건을 사람이 짐작한다.** 어떤 조건을 바꿔 볼지, 몇 번 할지를 경험으로 정한다 | 통계 분석은 과거를 설명하지만 다음 조건을 말해 주지 않는다 |
| P3 | **데이터가 흩어진다.** 엑셀·노트·메신저에 흩어져 모델을 만들 만한 표가 없다 | v2 데이터 허브로 모으기는 했지만, 모은 뒤 쓰는 길(예측·제안)이 없었다 |
| P4 | **목표 대비 어디까지 왔는지 한눈에 안 보인다** | v2에서 고객 요구 판정을 만들었다(유지) |

## 2. 해결 방향

> **"조건은 앱이 정하고, 사람은 결과 숫자만 넣는다."**

- 프로젝트 = 입력(바꿀 조건과 범위) + 측정 시점(선택) + 출력(측정 결과) + 목표.
- 앱이 실험 순서를 정한다. 처음엔 범위를 고르게 덮는 탐색 설계, 데이터가 쌓이면 모델이 목표를 향해 제안.
- 사람의 일은 "다음 실험 카드"에 적힌 조건대로 실험하고 결과 숫자를 넣는 것. 클릭은 저장 버튼 하나.
- 절차·단계·메모 체크리스트는 없앴다. 조건과 결과만 쌓이고, 그 표가 그대로 학습 데이터다.

성공 기준
- 실험 한 건 등록: 숫자 입력 n개(출력 수) + 클릭 1회.
- 새 프로젝트 시작: 변수 몇 줄과 목표를 적으면 첫 계획까지 자동.
- 예시 데이터(콘크리트)에서 교차검증 R² 0.8 이상, 목표 만족 조건 제안이 목표를 넘는다.

## 3. 데이터 모델 (`domain/types.ts`)

```
Project { id, name, note, variables: Variable[], goals: Goal[], initialRuns }
Variable { id, name, unit, role: input | level | output, min?, max?, decimals, levels? }
Goal     { id, variable, op: >= | <= | between, lo?, hi?, at?: {variable, value}, must }
Run      { id, project, order, x: {varId: 값}, y: {varId: 값}, status: planned | done | skipped, source, note, date }
```

- `input`: 앱이 값을 정해 주는 조건. 범위(min·max) 안에서 탐색한다. min = max면 고정.
- `level`: 재령처럼 정해진 몇 가지 값에서 재는 조건. 조건 하나마다 각 level 값에서 한 번씩 잰다. 목표의 적용 조건(`at`)에서 자동으로 채운다.
- `output`: 측정 결과. 목표는 보통 여기에 건다. 입력에 걸면(시멘트 ≤ 300) 탐색 범위를 좁힌다.
- 저장은 localStorage 한 키(`lablog.v3`)에 JSON 통째로. 수천 건까지 문제없다.

## 4. 실험 계획 (`services/plan.ts`)

| 단계 | 방법 |
|---|---|
| 탐색 | 가운데 점 1개 + 라틴 하이퍼큐브 (N−1)개. N은 프로젝트의 "처음 탐색할 조건 수"(기본 8). 값은 변수의 소수 자릿수로 반올림 |
| 측정 시점 펼치기 | 조건 × level 값 조합 → 실험 여러 건. 순서는 조건 순, 그 안에서 level 오름차순 |
| 개선 | 계획이 바닥나면 자동. 모델이 믿을 만하면(교차검증 R² ≥ 0.3, 필수 목표 있음) `suggest(explore=0.35)`로 3조건. 아니면 탐색 조건 2~4개 더 |
| 제안 → 실험 | 화면의 후보나 "조건 바꿔 보기"에서 "다음 실험으로"를 누르면 다음 순서에 끼워 넣는다 |

현황(`status`)은 목표마다 판정 건수·만족 건수·가장 좋은 값, level을 뺀 입력이 같은 실험을 "조건 묶음"으로 묶어 필수 목표를 모두 만족한 묶음이 있으면 달성, 없으면 가장 가까운 묶음과 부족한 목표를 알려 준다.

## 5. 모델 (`services/model.ts`)

| 항목 | 방법 |
|---|---|
| 입력·출력 | 값이 달라지는 input·level 변수(8건 이상) → 각 output. 빈 값은 중앙값 |
| 모델 | 랜덤 포레스트(80그루, 잎 2건) vs 능형회귀(표준화, λ=1). 5겹 교차검증 R²가 큰 쪽 |
| 신뢰도 | 교차검증 R²와 평균 오차를 항상 표시. R² < 0.3이면 예측·제안에 쓰지 않는다 |
| 불확실성 | 교차검증 잔차 표준편차 ⊕ 나무들의 흩어짐(본 적 없는 조건일수록 커짐) |
| 목표 만족 확률 | Φ(여유 ÷ 오차). 필수 목표의 곱 |
| 제안 | 관측 범위 안 무작위 1,500점 + 과거 조건 → 점수(필수 log 확률 합, 참고 0.2배, 탐색 가중치 × 모델 불확실성, 이미 계획한 조건 회피) → 상위 15개 다듬기 → 서로 다른 3개 |

예시 데이터 결과(콘크리트): SM-00 232건 R² 0.90, ES-30 R² 0.90, LF-20 R² 0.62(선형), HB-50 R² 0.78. 학습 0.2~0.3초, 제안 50 ms. HB-50의 "28일 ≥ 80 MPa"는 가장 좋은 후보도 14%로, 지금 범위에서는 어렵다는 것을 숫자로 보여 준다.

## 6. 어디까지 믿어도 되는가

- 모델은 실험한 범위 안에서만. 제안은 범위 안에서만 하고, 직접 넣은 값이 범위를 벗어나면 경고한다.
- 확률은 정규 가정 위의 근사. 실험이 적을수록(특히 30건 미만) 흔들린다. 후보도 실험으로 확인한다.
- 문자 조건(기재 종류 등)은 아직 입력에 쓰지 않는다. 숫자만.
- 프로젝트 안의 실험만 쓴다. 제품이 다르면 경향이 다르기 때문이다.

## 7. v2(실험 노트)에서 가져오는 것

"백업 가져오기"에 v2 백업 JSON을 넣으면 프로젝트마다 조건 이름 → 입력(범위는 데이터의 최소·최대), 결과 이름 → 출력, 고객 요구 → 목표(적용 조건은 level)로 바뀐다. 절차·단계·메모·첨부는 옮기지 않는다. 숫자가 아닌 값은 버린다.

## 8. 남은 것

- 문자 조건 입력(원-핫).
- 두 프로젝트를 묶어 학습(비슷한 제품군, 실험 적은 새 프로젝트).
- "이 조건은 고정하고 나머지만 찾기"(계산은 `suggest(fixed)`로 준비됨).
- 팀 공유(지금은 브라우저 하나). 파일 백업으로 주고받는다.
