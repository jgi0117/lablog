# 개발 계획 (Dev Plan): 실험 기록 서비스

**문제**: 실험 기록이 여러 곳에 흩어져 찾기도 재현하기도 어려운 문제
**기준 문서**: prd.md(범위·KR), IA.md(화면·URL), uj.md(흐름·오류), 문제정의-솔루션.md
**범위**: 0단계 준비 → 최종 테스트·파일럿까지 + 이후 Supabase 전환 계획
**현재 저장 방식**: 로컬 전용(브라우저). 추후 Supabase 도입.

---

## 0. 한눈에 보기

- **Phase 0. 준비**: 결정 확정, 환경 구성, 가정 검증 시작
- **Phase 1. 설계**: 와이어프레임, 데이터 모델, 화면 설계
- **Phase 2. 기반 구축**: 프로젝트 뼈대, 저장소 계층, 공통 UI
- **Phase 3. s1 모으기**: 실험 생성, 수행 모드, 조건·결과
- **Phase 4. s2 찾기**: 목록·분류·검색
- **Phase 4.5. s4 살펴보기**: 프로젝트 화면, 빠짐 점검, 데이터 표, 차트, 이상치 후보 (사원 개인용 차별점, 안정화보다 먼저)
- **Phase 5. 안정화**: 오류 처리, 백업, 접근성, 성능
- **Phase 6. 최종 테스트**: 단위·통합·E2E·사용성 테스트, KR 측정
- **Phase 7. 파일럿 출시**: 1팀 운영, 피드백, KR 평가
- **Phase 8. s3 다시 쓰기**: 복제·템플릿·편차 (검증 후 범위 결정)
- **Phase 9. Supabase 전환**: 인증, DB, 동기화, 데이터 이전 (이후)

각 Phase는 **완료 기준(DoD)을 통과해야 다음으로** 넘어갑니다.

## 1. 핵심 결정과 가정

### 1.1 기술 스택 (제안, 확정 필요)

- **형태**: 웹 앱(SPA). PC와 태블릿 브라우저에서 사용 [가정: 확인 필요 4번]
- **프론트엔드**: Vite + React + TypeScript
- **라우팅**: React Router (IA.md의 URL 그대로)
- **로컬 저장**: IndexedDB (Dexie 래퍼). 용량과 구조화된 조회에 유리. localStorage는 설정 값만.
- **검색**: 클라이언트 전문 검색 (MiniSearch 등 가벼운 라이브러리)
- **상태 관리**: React 상태 + 저장소 훅 (필요하면 Zustand)
- **테스트**: Vitest(단위·통합), React Testing Library, Playwright(E2E)
- **품질 도구**: ESLint, Prettier, TypeScript strict
- **배포**: 정적 호스팅(Vercel, Netlify 등). 서버 없음.
- **PWA(선택)**: 오프라인 실행·홈 화면 추가. 실험대 환경(네트워크 불안정)에 유리.

대안: 기존 프로젝트들처럼 Python 서버 + 순수 HTML/JS도 가능합니다. 다만 Supabase 전환, 컴포넌트 재사용(IA의 Component Reuse Map), 테스트 도구 면에서 위 스택이 유리합니다.

### 1.2 아키텍처 원칙: "저장소를 갈아끼울 수 있게"

로컬 → Supabase 전환을 쉽게 하기 위해 **화면은 저장소를 직접 부르지 않고 Repository 인터페이스만 부른다.**

```
UI(React 컴포넌트)
  → 훅(useExperiments 등)
    → Service(도메인 로직: 검증, 진행률 계산)
      → Repository 인터페이스 (ExperimentRepository 등)
          ├─ LocalRepository (IndexedDB)       ← 지금
          └─ SupabaseRepository (Postgres)     ← 나중
```

- 모든 ID는 **UUID**(클라이언트 생성). Supabase에서 그대로 쓸 수 있고, 오프라인 생성에 유리.
- 모든 레코드에 `createdAt`, `updatedAt`, `deletedAt`(소프트 삭제), `version` 포함. 동기화·휴지통·충돌 감지에 필요.
- 날짜는 ISO 8601 문자열(UTC).
- 도메인 타입은 저장소와 무관하게 `domain/`에 정의.
- 저장소 호출은 전부 `async`(Promise). 로컬이라도 동기 호출 금지(전환 시 변경 최소화).

### 1.3 확인이 필요한 가정과 개발에 미치는 영향

- **수행 중 기기 입력 가능?** 불가면 → 수행 모드의 "사후 입력" 보조 흐름 추가. 가능하면 큰 버튼·터치 최적화 우선.
- **사용 기기** PC+태블릿이 아니고 모바일 중심이면 → 레이아웃을 모바일 우선으로 재설계.
- **클라우드 저장 가능?** 불가면 → Phase 9에서 Supabase 대신 사내 서버·로컬 유지 검토.
- **개인 vs 팀 공유 우선순위** → 인증·권한 설계 시점(Phase 9) 결정.

## Phase 1. 설계

**목표**: 구현자가 헷갈리지 않을 수준까지 화면·데이터·흐름을 확정한다.

### 1.1 와이어프레임 (저충실도)
IA.md의 Content Hierarchy 기준으로 화면 8개를 그린다.
- [ ] 홈(대시보드): 진행 중 실험 → 미완료 단계 → 최근 실험
- [ ] 실험 목록: 검색창·필터·카드·정렬
- [ ] 실험 만들기: 제목(필수), 목적, 프로젝트, 태그
- [ ] 실험 상세 개요 / 조건·결과 / 첨부 / 편차 탭
- [ ] **수행 모드**(최우선): 현재 단계 강조, 체크, 메모·수치 입력, 진행률, 이전·다음
- [ ] 검색 결과: 하이라이트, 필터, 정렬
- [ ] 빈 상태(실험 0건, 검색 결과 없음), 로딩, 오류 상태
- [ ] 태블릿 가로·세로, PC 폭 3가지 레이아웃

### 1.2 수행 모드 사용성 사전 검증
- [ ] 종이 프로토타입 또는 클릭 가능한 목업으로 연구원 2~3명에게 시연 (장갑 낀 상태 포함)
- [ ] 터치 영역 최소 44px 이상, 체크 영역을 크게 (uj.md 마찰 대응)

### 1.3 데이터 모델 확정

**Project**: id, name, description, 공통 필드
**Experiment**: id, projectId, title, purpose, status(`ready`|`running`|`done`), owner, tags[], startedAt, completedAt, 공통 필드
**Step**: id, experimentId, order, content, done(boolean), doneAt, note, 공통 필드
**DataItem**: id, experimentId, kind(`condition`|`result`), name, value, unit, 공통 필드
**Attachment** (P1): id, experimentId, stepId?, fileName, mimeType, size, blobRef, 공통 필드
**Deviation** (s3): id, experimentId, stepId, change, reason, 공통 필드
**Template** (s3): id, name, steps[], defaultConditions[], 공통 필드
**Tag**: 실험의 `tags[]` 문자열 배열로 시작. 태그 병합 기능이 필요해지면 별도 테이블로 분리.
**Settings**: 마지막 선택 필터, 스키마 버전 등 (localStorage 또는 별도 store)

- [ ] 상태 전이 규칙: `ready → running → done`, `done → running`(재개) 허용
- [ ] 진행률 = 완료 단계 수 / 전체 단계 수 (단계 0개면 0%)
- [ ] 삭제 = `deletedAt` 설정(휴지통 30일). 30일 후 영구 삭제.
- [ ] 로컬 DB 버전·마이그레이션 규칙 (스키마 버전 정수, 업그레이드 함수)

### 1.4 Repository 인터페이스 정의
- [ ] `ExperimentRepository`: `list(filter, sort, page)`, `get(id)`, `create`, `update`, `softDelete`, `restore`, `search(query, filter)`
- [ ] `StepRepository`: `listByExperiment`, `upsert`, `reorder`, `toggleDone`
- [ ] `DataItemRepository`: `listByExperiment`, `upsert`, `remove`
- [ ] `ProjectRepository`, (P1) `AttachmentRepository`, (s3) `TemplateRepository`, `DeviationRepository`
- [ ] 백업용 `exportAll()`, `importAll(json)`
- [ ] 계약 테스트 스펙: **어떤 Repository 구현이든 같은 테스트를 통과**해야 함 (Phase 9에서 재사용)

### 1.5 UI 기준
- [ ] 디자인 토큰: 색, 글자 크기(수행 모드는 크게), 간격, 터치 크기
- [ ] 공통 컴포넌트 목록: 실험 카드, 단계 체크 항목, 이름-값-단위 입력 행, 필터 바, 빈 상태, 토스트(되돌리기), 확인 다이얼로그
- [ ] 용어 사전 적용: "실험", 준비/진행/완료, "절차와 달라진 점"

### 1.6 테스트 계획 초안
- [ ] 테스트 데이터 세트 설계 (아래 6.1)
- [ ] uj.md의 오류 시나리오를 테스트 케이스 목록으로 변환

**DoD**: 화면 8개 와이어프레임과 데이터 모델·Repository 인터페이스가 문서화되고, 연구원 1명 이상이 수행 모드 목업을 보고 "쓸 만하다"고 확인.

## Phase 2. 기반 구축

**목표**: 기능을 얹을 뼈대. 이 단계에서 "저장소 교체 가능 구조"를 완성한다.

### 2.1 프로젝트 구조

```
src/
  domain/          타입·규칙 (Experiment, Step, 진행률 계산, 상태 전이)
  data/
    repositories/  인터페이스 (ExperimentRepository 등)
    local/         IndexedDB 구현 (Dexie)
    supabase/      (Phase 9에서 추가, 지금은 비어 있음)
    index.ts       어떤 구현을 쓸지 선택하는 한 곳
  services/        도메인 로직 (검색 색인, 백업, 검증)
  hooks/           useExperiments, useStepRunner 등
  components/      공통 UI
  pages/           라우트 단위 화면 (IA.md URL과 1:1)
  styles/          토큰·전역 스타일
  tests/           계약 테스트, 픽스처
e2e/               Playwright 시나리오 (journeys)
```

### 2.2 작업
- [ ] Vite+React+TS 프로젝트 생성, ESLint/Prettier/strict 설정
- [ ] 라우팅: `/`, `/experiments`, `/experiments/new`, `/experiments/:id`, `/experiments/:id/steps`, `/experiments/:id/data`, `/search`, `/settings`
- [ ] 앱 레이아웃: 상단(전역 검색창, + 새 실험, 설정), 메인 메뉴(홈·실험·검색·템플릿)
- [ ] 도메인 타입과 규칙 구현 + 단위 테스트(진행률, 상태 전이)
- [ ] Dexie 스키마 v1, `LocalRepository` 구현 (Project, Experiment, Step, DataItem)
- [ ] Repository **계약 테스트** 작성 후 LocalRepository 통과
- [ ] `data/index.ts`에서 구현 주입 (환경 변수로 `local` 선택)
- [ ] 공통 컴포넌트 스켈레톤 (빈 상태, 토스트, 다이얼로그)
- [ ] 저장 상태 표시 컴포넌트 ("저장됨 / 저장 중 / 저장 실패")
- [ ] 테스트 픽스처: 샘플 실험 생성 함수, 개발용 "샘플 데이터 넣기" 버튼
- [ ] CI 설정: 푸시마다 린트·타입체크·단위 테스트 (GitHub Actions 등)

**DoD**: 빈 화면들이 라우팅으로 이동되고, 샘플 데이터를 저장·조회·삭제하는 계약 테스트가 모두 통과하며, CI가 초록불.

## Phase 3. s1 모으기

**목표**: Journey 1(새 실험 수행)을 끝까지 쓸 수 있다. 이 Phase가 제품의 핵심.

### 3.1 실험 만들기 (`/experiments/new`)
- [ ] 폼: 제목(필수), 목적, 프로젝트, 태그
- [ ] 검증: 제목 비어 있으면 안내. 나머지는 선택.
- [ ] 생성 후 절차 탭으로 이동 (입력 3번 이내 생성 달성)
- [ ] 프로젝트 즉석 생성(드롭다운에서 "새 프로젝트")
- 테스트: 제목만 입력해 생성, 제목 없이 제출 시 오류, 태그 입력 복수

### 3.2 절차 편집 + 수행 모드 (`/experiments/:id/steps`)
- [ ] 단계 추가·수정·삭제·순서 변경 (준비 상태에서)
- [ ] 텍스트 붙여넣기로 여러 단계 한 번에 생성 (줄바꿈 기준)
- [ ] **수행 모드 시작**: 상태가 `running`으로 바뀌고 전체 화면으로 전환
- [ ] 현재 단계 강조, 체크 영역 크게(44px 이상), 이전·다음 이동
- [ ] 체크 시 즉시 저장 + 진행률 갱신 + "저장됨" 표시
- [ ] 단계별 메모, 수치 입력 (체크와 같은 화면)
- [ ] 체크 실수 대응: 체크 해제 가능 + 5초 되돌리기 토스트 (E2)
- [ ] 단계 건너뛰기 허용하되 완료 때 경고 (E3)
- [ ] 입력 자동 저장(디바운스 300~500ms), 앱 닫아도 유지 (E1의 로컬 부분)
- [ ] 키보드 접근: 스페이스로 체크, 화살표로 이동
- 테스트: 체크→새로고침→유지, 되돌리기, 건너뜀 경고, 진행률 계산

### 3.3 조건·결과 (`/experiments/:id/data`)
- [ ] 이름-값-단위 행 추가·수정·삭제, 구분(조건/결과)
- [ ] 단위는 선택식 + 직접 입력 가능, 자주 쓴 이름·단위 자동 완성
- [ ] 수치 형식 검증(숫자 아닌 값은 경고, 막지는 않음), 범위 이상 값은 확인 질문 (E7)
- [ ] 완료 처리: 비어 있는 결과·미완료 단계 목록 안내, "나중에 입력" 선택 가능
- [ ] 완료 → 상태 `done`, `completedAt` 기록

## Phase 5. 안정화

**목표**: 로컬 전용 앱에서 가장 무서운 "데이터 유실"과 현장 사용성을 잡는다.

### 5.1 데이터 보호 (로컬 전용의 핵심 리스크)
- [x] **내보내기**: 전체 데이터 JSON 파일로 저장 (설정 화면, 저장 실패 안내, 용량 경고, 홈 알림에서 같은 기능)
- [x] **가져오기**: JSON 검증(버전, 필수 필드, id 중복, 주인 없는 단계, 파일 크기) 후 합치기 또는 바꾸기 선택, 미리보기(건수) 표시. 바꾸기는 확인을 거치고 먼저 현재 데이터를 자동 백업하며, 그 백업이 실패하면 중단
- [x] 백업 알림: 한 번도 백업하지 않았고 첫 기록이 하루 넘었거나, 마지막 백업 뒤 바뀐 것이 있고 7일이 지나면 홈에 안내. "3일 뒤에 다시"
- [x] 브라우저 저장소 영구화 요청(`navigator.storage.persist()`)과 결과 표시. 거부되면 설정에서 이유와 백업을 안내
- [x] 스키마 마이그레이션: DB v2(복합 인덱스 추가, 빠진 필드 채우기)와 v1 → v2 업그레이드 테스트
- [x] 저장 실패 처리: 저장소를 열 수 없으면(사생활 모드 등) 모든 화면 위에 경고, 용량 80% 이상이면 경고와 바로 백업. 입력 저장이 실패하면 다시 시도와 데이터 내보내기
- [x] 여러 탭: BroadcastChannel로 다른 탭의 변경을 알려 "새로 고침"을 권하고, 저장할 때 version을 비교해 충돌하면 "최신 내용 불러오기 / 내 내용으로 덮어쓰기"

### 5.2 오류·예외 마무리 (uj.md 전체 점검)
- [x] E1 연결 끊김: 로컬 전용이라 동작에 영향 없음(저장소는 기기 안)
- [ ] 앱을 PWA로 만들어 오프라인 실행(선택) — Phase 7 배포 때 판단
- [x] 오류 경계: 화면 하나가 깨져도 메뉴는 남고, 앱 전체 경계는 마지막 안전망. 오류 기록(처리하지 못한 오류 포함)은 설정에서 보고 지울 수 있음
- [x] 파괴적 동작에 확인 또는 되돌리기: 삭제는 되돌리기, 영구 삭제와 바꾸기 가져오기는 확인창

### 5.3 접근성·사용성
- [x] 본문으로 건너뛰기, 포커스 표시, 라벨, 차트의 스크린 리더 요약과 키보드 조작
- [ ] 키보드만으로 핵심 흐름을 처음부터 끝까지 확인 — 구성 요소는 갖췄지만 사람이 직접 해 본 확인은 남음

- [ ] 수행 모드 큰 글씨·큰 버튼 확인(태블릿 실기기)
- [x] 화면 꺼짐 방지(Wake Lock) 설정: 수행 중 화면이 꺼지지 않게, 설정에서 끌 수 있음

### 5.4 성능
- [x] 실험 500건·단계 4,000개: 목록 묶음 읽기 22ms, 검색 처음 26ms 이후 3ms(테스트 환경). 홈·프로젝트가 실험마다 따로 읽던 것을 한 번에 읽도록 바꿈. 목록은 12개씩 나눠 가상 스크롤은 불필요
- [x] 코드 분할: 프로젝트·차트·설정 화면은 열 때 불러옴
- [ ] 실제 브라우저와 태블릿에서 첫 화면 시간·체크 반응 측정 — 파일럿 기기에서 확인

### 5.5 계측 (로컬 전용이므로 기기 내 기록)
- [x] KR 측정 이벤트: 검색→열기 시간, 단계 체크, 완료 시 미완료 단계·빈 결과 수, 빠진 것 개수(6시간에 한 번), CSV·백업 내보내기

**DoD**: 내보내기→초기화→가져오기로 데이터가 100% 복원되고, 접근성·성능 목표를 만족.

## Phase 8. s3 다시 쓰기 (파일럿 결과 후 범위 확정)

우선순위는 파일럿 피드백으로 조정합니다. 기본 순서:

1. **복제 + 템플릿으로 저장** (Journey 3 Step 1) — 구현 완료
   - 복제: 절차·조건 유지, 결과·체크·메모 비움, 안내 문구
   - 템플릿 목록·편집(`/templates`), 템플릿에서 새 실험 시작
   - 테스트: 복제 후 결과 비어 있음(E1), 원본 불변
2. **편차 기록(달라진 점)** (Journey 3 Step 3) — 구현 완료: 대상 단계·변경 내용·사유, 편차 탭, 수행 모드에서 2탭 이내 입력
3. **가져오기(엑셀·텍스트 붙여넣기)**: 도입 장벽 낮추기
4. **팀 대시보드**: Supabase 도입(Phase 9) 이후로 미루는 것을 권장 (공유 데이터가 필요하므로)

각 항목은 Phase 3~4와 같은 방식(기능 → 테스트 → E2E → DoD)으로 진행.

## Phase 9. Supabase 전환 (파일럿 평가 후)

**목표**: 같은 앱을 서버 저장소로 옮겨 기기 간 동기화·팀 공유를 가능하게 한다. **UI는 거의 바꾸지 않는 것이 성공 기준.**

### 9.0 전환 전 판단
- [ ] 필요성 확인: 여러 기기 사용, 팀 공유, 백업 부담이 파일럿에서 실제 문제로 나왔나
- [ ] 보안 정책 확인(가정 4): 외부 클라우드 저장 허용 여부, 데이터 지역
- [ ] 사용자 범위: 개인 우선 vs 팀 공유 우선

### 9.1 Supabase 프로젝트 준비
- [ ] 프로젝트 생성, 환경 분리(개발/운영)
- [ ] 키 관리: 공개용 anon 키만 프론트에, 서비스 키는 절대 프론트에 넣지 않음
- [ ] 로컬 개발용 Supabase CLI 사용, 스키마는 **마이그레이션 파일로 버전 관리**

### 9.2 스키마 (Postgres)
도메인 모델을 그대로 옮긴다.
- 테이블: `projects`, `experiments`, `steps`, `data_items`, `attachments`, `deviations`, `templates`, `tags`(필요 시)
- 공통 컬럼: `id uuid`, `created_at`, `updated_at`, `deleted_at`, `version`, **`owner_id`**(auth.users 참조)
- 로컬에서 쓰던 UUID와 필드명을 그대로 사용해 이전을 단순하게
- 인덱스: `experiments(owner_id, status, updated_at)`, 전문 검색용 `tsvector` 열 + GIN 인덱스(한국어 검색 방식 검토: `pg_trgm` 부분 일치 병행)
- 첨부 파일은 DB가 아니라 **Storage 버킷** (경로 규칙: `{owner_id}/{experiment_id}/{file}`)

### 9.3 인증과 권한
- [ ] 이메일 로그인(매직 링크) 우선, 기관 SSO는 필요 시
- [ ] **RLS(Row Level Security) 필수**: `owner_id = auth.uid()` 기준 기본 정책
- [ ] 팀 공유 시: `teams`, `team_members` 테이블, 정책을 "본인 또는 같은 팀"으로 확장
- [ ] 역할: 연구원(편집), 팀장(열람·현황), 신규 입사자(복제·편집)
- [ ] RLS 정책 테스트(다른 사용자의 데이터가 안 보이는지)를 자동화

### 9.4 SupabaseRepository 구현
- [ ] Phase 1의 인터페이스를 그대로 구현
- [ ] **Repository 계약 테스트를 그대로 실행**해 통과 확인 (LocalRepository와 동일 결과)
- [ ] 검색: 서버 검색(`tsvector`/`pg_trgm`)으로 교체. 결과 형식은 동일하게 맞춤.
- [ ] 에러 매핑: 네트워크 오류, 권한 오류, 충돌을 앱 공통 오류 타입으로 변환

### 9.5 오프라인·동기화 전략 (실험실 현장 고려)
단계적으로 도입한다.
- **1단계(권장 시작)**: 온라인 우선 + 로컬 쓰기 큐. 오프라인이면 로컬(IndexedDB)에 쓰고 연결되면 서버로 전송. "저장 대기 중" 표시(E1 설계 그대로).
- **2단계**: 충돌 처리. `version` 비교로 감지, 단계 단위 병합, 같은 필드 충돌은 사용자에게 선택 요청(E6/E9).
- **3단계(필요 시)**: Realtime 구독으로 팀원 변경 즉시 반영.
- 삭제는 `deleted_at`으로 동기화(물리 삭제 금지).

### 9.6 로컬 → Supabase 데이터 이전
- [ ] 이전 도구: 앱 안의 "클라우드로 이전" 마법사 (처음 로그인 시)
- [ ] 순서: 로컬 백업 자동 생성 → 건수 미리보기 → 업로드(프로젝트→실험→단계→데이터→첨부) → 건수·체크섬 검증 → 완료 표시
- [ ] 멱등성: UUID 유지로 **중단 후 재실행해도 중복 없음**
- [ ] 로컬 데이터는 이전 확인 후에도 **일정 기간 보관**(되돌릴 수 있게), 사용자가 삭제 결정
- [ ] 이전 실패 시 로컬 사용 계속 가능

### 9.7 전환 테스트
- [ ] 계약 테스트(Local·Supabase 동일 통과)
- [ ] RLS 침투 테스트(다른 계정 접근, 키 노출 점검)
- [ ] E2E를 Supabase 저장소로 재실행(J1, J2, J3)
- [ ] 오프라인→온라인 동기화 시나리오, 충돌 시나리오
- [ ] 이전 도구: 건수 큰 데이터(L 세트) 이전, 중단·재시작
- [ ] 성능: 서버 왕복 지연에서 체크 반응 즉시성(낙관적 업데이트), 검색 2초

### 9.8 단계적 전환
- [ ] 기능 플래그로 저장소 선택 (`local` / `supabase`)
- [ ] 파일럿 일부 사용자만 Supabase 사용 → 문제 없으면 확대
- [ ] 롤백 계획: 플래그를 local로 되돌리고, 서버 데이터는 내보내기로 확보

**DoD**: 같은 E2E가 Supabase 모드에서 통과, RLS 테스트 통과, 로컬 데이터 이전이 건수·내용 검증을 통과.

## 2. 품질 기준 (모든 Phase 공통)

- **PR마다**: 린트·타입체크·단위 테스트 통과, 변경한 화면은 스크린샷 첨부, 용어 사전 준수
- **기능 완료 기준**: (1) 수용 기준 충족 (2) 테스트 작성 (3) 빈 상태·오류 상태 처리 (4) 키보드·터치 확인
- **데이터 안전 원칙**: 파괴적 동작은 항상 되돌릴 수 있거나 확인을 받는다. 스키마 변경은 마이그레이션 + 테스트 없이 배포하지 않는다.
- **범위 관리**: 새 요구는 s1~s3 어디에 속하는지, KR에 기여하는지 먼저 적는다. 해당 없으면 백로그.

## 3. 위험과 대응

- **로컬 데이터 유실** (브라우저 데이터 삭제, 기기 교체): 내보내기·백업 알림, 영구 저장소 요청, 첫 실행 안내
- **수행 중 입력이 현장에서 불편**: Phase 1에서 목업 검증, 사후 입력 보조 흐름 준비, 큰 버튼
- **가정이 틀림(재실험 원인이 절차가 아님)**: Phase 0 검증 결과로 우선순위 조정, 편차·템플릿 먼저 여부 재판단
- **한국어 검색 품질**: 부분 일치 기반으로 시작, 실제 검색어 로그로 보정
- **Supabase 전환 때 UI 대수술**: Repository 계약 테스트와 UUID·소프트 삭제 설계로 방지
- **범위 팽창**: 첫 버전 = s1 + s2(분류·통합 검색). 첨부·s3는 파일럿 이후
- **보안·규제**: 클라우드 저장 가능 여부를 Phase 9 이전에 확인. 규제(GLP 등)는 이번 범위 밖임을 명시
