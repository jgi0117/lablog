# lablog-v2 문제 정의

2026-10-20 사용자 대화로 제품 방향을 다시 정했다. 확인된 사실만 사실로 쓰고 나머지는 `[가정]`이다. 용어는 `GLOSSARY.md`를 따른다.

## 지금(lablog v1)의 상태

사실(코드·QA로 확인):
- 실험 생성 화면은 제목만으로 저장할 수 있고, 프로젝트 화면에서 들어오면 프로젝트를 미리 선택한다.
- 같은 프로젝트의 마지막 실험에서 절차·조건·결과 항목을 이어받을 수 있다. 조건 값은 유지하고 결과 값은 비운다.
- 생성 화면에 목적·프로젝트·태그·템플릿·마지막 실험 이어받기가 한꺼번에 있어 선택할 것이 많다.
- 실험 목록은 제목·상태·진행률 중심이고, 주요 조건·결과·편차는 상세 화면을 열어야 확인할 수 있다.
- 검색과 템플릿이 각각 별도 화면과 주 내비게이션을 차지한다.
- 앱에는 기록·수행 모드, 프로젝트 현황, 빠짐 점검, 데이터 표·분석, 백업·로그인까지 구현돼 있다.
- 구조 재구성 1단계가 끝났다. 300줄 초과 파일 10개와 현재 폴더 구조는 후속 작업 대상이다.

## 문제

**기능은 많지만 실험을 편리하게 등록하고, 기록의 핵심을 한눈에 파악하는 경험이 중심에 있지 않다.**

- 반복 실험에서도 사용자가 무엇을 가져올지 판단하고 여러 입력을 다시 확인해야 한다.
- 목록만 보고는 실험의 목적, 주요 조건과 결과, 달라진 점을 파악하기 어렵다.
- 프로젝트 안에서 최근 실험의 결과와 다음 실험의 연결이 약하다.
- 검색·템플릿이 독립 기능으로 존재해 핵심 흐름보다 제품 구조가 복잡하다.

이 상태에서는 기록을 남겼어도 다시 상세 화면을 오가거나 별도로 정리해야 하므로, 종이·엑셀·메모를 대체한다는 목적을 충분히 달성하지 못한다.

## 목표 (v2)

1. **편리한 등록**: 앱이 프로젝트 맥락과 이전 실험을 기억하고, 사용자는 달라진 부분만 입력한다.
2. **한눈에 보는 기록**: 실험 목록과 개요에서 목적·상태·진행률·주요 조건·결과·편차·수정 시각을 빠르게 파악한다.
3. **프로젝트 흐름**: 프로젝트에서 진행 중 실험, 최근 결과, 빠진 기록과 다음 실험 진입점을 함께 본다.
4. **집중된 구조**: 별도 검색·템플릿 화면은 제거한다. 실험 목록의 최소 검색·필터와 이전 실험 이어받기는 유지한다.
5. **안전한 기반**: 기존 데이터·백업 형식을 보존하고, 구조 재구성·시험·문서 일치를 계속한다.

핵심 가치 우선순위: **등록 편의 → 기록 파악 → 프로젝트 검토 → 분석**.

## 사용자

개인 연구원 1명(파일럿). 여러 프로젝트와 반복 실험을 병행하며 PC·태블릿을 쓴다. 실험대에서 장갑을 낀 채 입력하는 상황은 `[가정]`이며 현장 확인이 필요하다.

## 제약

- 작업은 `lablog-v2`의 `v2` 브랜치에서만 한다. `main`과 `../lab`은 건드리지 않는다.
- 기존 실험·템플릿 데이터와 백업을 삭제하지 않는다.
- 템플릿 UI를 제거해도 `templates` 표는 데이터 보존을 위해 유지한다. 표 삭제는 별도 승인 없이는 하지 않는다.
- 새 라이브러리, 표 구조 변경, 사용자에게 보이는 동작 변경은 spec/plan 확정 뒤 진행한다.
- 접근성, 390px 반응형, 다크 모드, 자동 저장·충돌 감지를 유지한다.

## 성공 기준

- SC-A. 프로젝트에서 시작하면 프로젝트가 이미 선택되고, 제목만 입력해 실험을 만들 수 있다.
- SC-B. 반복 실험은 이전 실험의 절차·조건·결과 항목을 이어받고 달라진 부분만 고친다. 이전 결과 값과 단계 체크·메모는 복사되지 않는다.
- SC-C. 실험 목록에서 최근 실험 10건의 상태·진행·주요 조건·결과·수정 시각을 상세 화면을 열지 않고 비교할 수 있다.
- SC-D. 실험 개요 첫 화면에서 “왜 했는지, 어떻게 진행됐는지, 무엇이 나왔는지”를 파악할 수 있다.
- SC-E. 별도 검색·템플릿 내비게이션 없이 실험 목록의 키워드·프로젝트·상태·기간 필터로 필요한 실험을 찾는다.
- SC-F. 기존 데이터와 백업 형식이 보존되고 `npm run check` 450개·E2E 112개 기준선이 새 요구사항에 맞게 갱신되어 통과한다.
- SC-G. 모든 코드 파일 300줄 이하, import 경계 위반 0건이라는 구조 목표를 유지한다.

## 열린 질문

1. 실험에 명시적인 `결론`과 `다음 행동` 필드를 추가할지 사용자 확인이 필요하다. 추가하면 표 구조 변경과 마이그레이션이 필요하다.
2. 기존 템플릿 데이터는 삭제하지 않고 백업에 계속 포함하되 화면만 숨기는 것을 기본으로 한다.
3. 데이터 허브의 고급 통계는 현 상태를 유지하되 이번 핵심 경험 작업에서는 확장하지 않는다.
4. “30초 안에 등록”, “최근 10건을 10초 안에 파악” 기준이 현장에 맞는지는 직접 QA에서 측정한다.
5. 실험대에서 수행 중 기기 입력이 가능한지 관찰이 필요하다.
