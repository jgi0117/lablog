## 1. 기술과 버전

무엇으로 만드나. **버전은 추측하지 말고** `app/package.json`과 `app/package-lock.json`에서 읽어 정확히 쓴다.

| 이름 | 정확한 버전 | 용도 | 새로 들이나? |
|---|---|---|---|
| (예: React) | (package.json 값) | 화면 | 아니오(기존) |

- **새 라이브러리는 되도록 들이지 않는다.** 들여야 하면 이유, 대안(직접 만들면 얼마나 드는지), 크기, 마지막 갱신, 라이선스를 적고 사용자에게 먼저 묻는다.
- 서버 쪽(Supabase): 바꾸는 표·정책·함수는 2번에, 적용은 새 마이그레이션 파일로만 한다.

## 2. 구조와 파일

**폴더와 파일**: 바꾸거나 새로 만드는 것만 적고, 파일마다 하는 일을 한 줄로 쓴다. 새 파일은 비슷한 기존 파일 옆에 둔다.

```text
app/src/
  pages/XxxPage.tsx        ← (수정) …
  services/xxx.ts          ← (신규) …
supabase/migrations/
  YYYYMMDDHHMMSS_xxx.sql   ← (신규) …
```

**데이터(표 모양)**: ERD(`docs/phase9/erd.md`)에서 바뀌는 부분만. 열 이름·형식·기본값·널 허용, 외래 키, 보안(RLS) 정책, 인덱스. 앱 필드(camelCase)와 DB 열(snake_case) 대응은 `app/src/data/supabase/mapping.ts`에 한 곳에서 적는다.

**요구사항 ↔ 파일**: 요구사항이 어느 파일에서 구현되는지.

| 요구사항 | 파일 | 비고 |
|---|---|---|
| FR-1 | `app/src/…` | |

## 3. 단계별 접근

몇 단계로 나눠 만드나. **각 단계가 끝나면 앱이 돌아가고 시험이 통과해야** 한다(한 번에 크게 바꾸지 않는다). 위험한 것(데이터 이전, 보안)을 앞에 둔다.

| 단계 | 목표 | 바꾸는 파일 | 끝났는지 확인 | 되돌리는 법 |
|---|---|---|---|---|
| 1 | | | (시험 이름 또는 눈으로 볼 것) | (커밋 되돌리기 / 마이그레이션 취소) |
| 2 | | | | |

- 단계마다 커밋한다(push는 사용자가 말할 때).
- 새 라이브러리는 되도록 안 들인다. 기존 코드·패턴(`DataBackend`, `useDebouncedSave`, `services/`)을 먼저 재사용한다.

## 4. 테스트 전략

무엇으로 확인하나. 요구사항·성공 기준마다 한 줄 이상.

**실행 명령** (전체 명령을 그대로 적는다)

```bash
npm --prefix app run check        # 타입 + 린트 + 단위·통합 시험
(cd app && npx playwright test)  # E2E (화면이 바뀌면)
npm --prefix app run test:supabase # 진짜 서버 계약·보안 시험 (시험용 프로젝트에서만)
```

| 성공 기준 | 방법 | 위치 |
|---|---|---|
| SC-1 | 함수 시험(Vitest) / 화면 눌러 보기(Playwright, Testing Library) / QA 시트 직접 확인 | `app/src/…test.ts` |

- **먼저 실패하는 시험을 쓰고** 구현한다(가능한 것은).
- 서버 보안(RLS)이 바뀌면 사용자 A·B 침투 시험을 추가한다(다른 사람 데이터 읽기·수정·삭제·위조 삽입).
- 직접 해봐야 하는 것은 QA 시트(`docs/phase9/03-QA-체크리스트.md` 형식)에 시나리오로 옮긴다.
- 시험 결과를 지어내지 않는다: 못 돌린 것은 "No Run"과 이유를 적는다.

## 5. 제약과 주의점

**세 단계 경계**

| 구분 | 내용 |
|---|---|
| **항상 한다** | (예: 변경 후 `npm run check`, 기존 시험 유지, 문서 갱신) |
| **먼저 묻는다** | (예: 새 라이브러리, 표 구조 변경, 기존 데이터 변경·삭제, 배포 설정) |
| **절대 안 한다** | (예: service_role 키를 앱·문서·대화에 넣기, 운영 데이터를 지우는 시험, 사용자 동의 없이 push) |

- **비밀 키**: `VITE_`로 시작하는 변수는 브라우저에 그대로 공개된다. 공개용 키만 둔다. 비밀번호는 사용자가 직접 입력한다.
- **속도**: (예: 목록 로딩 목표, 1,000건 이상에서도 느리지 않게. 측정 방법을 쓴다)
- **지금 돌아가는 기능을 깨지 않기**: 건드리는 기존 화면·함수 목록과, 그것을 지키는 기존 시험 이름.
- **되돌리기**: 데이터 구조를 바꾸면 백업 방법과 되돌리는 방법을 먼저 쓴다.
- **끝나면**: Intent.md 상태 갱신, 어긋난 PRD·IA·UJ·ERD 고치기, QA 시트 갱신.
